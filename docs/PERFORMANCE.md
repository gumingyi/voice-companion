# 0.4性能测量与优化

用户反馈提交后十多秒才显示回答。本次先检查实际配置：DeepSeek官方deepseek-flash、thinking disabled、背景约2730字符。因此不能把延迟直接归因于思考模式。

## 真实测量（2026-10-27）

使用本机凭据发送少量真实的两句回答诊断，输入约3713字符，诊断max_tokens最多256；没有保存Key、提示词、回答或思考内容。

- 原始冷连接：响应头0.485秒、正文首字1.016秒、完成1.610秒。
- 同会话连接复用：首字1.000秒、完成1.656秒；重复一次首字0.719秒、完成1.234秒。
- 新版真实桌面链路：提交到可见首字1.328秒，总计1.920秒；凭据读取0.015秒、接口响应头0.578秒、接口正文首字1.266秒。首字从收到到界面显示约毫秒级。

证据：verification/deepseek_latency.json、verification/deepseek_ui_latency.json。样本很少且服务端时变，不能用这些请求证明因果上的首字提速，更不能承诺每次都一秒。当前没有复现十多秒空白。

## 改动及意义

1. Controller持有HTTPX连接池，模型测试与生成复用；每个请求单独设置Authorization，避免跨配置凭据混用。连接超时最多8秒，总读写超时仍由配置控制。
2. 首个正文立即发布，后续文本以约50ms间隔合并界面与手机快照；最终结果强制刷新。历史列表签名不变时不重建，答案使用增量追加。高速流可避免主线程消息积压。
3. 增加快速回答开关：完整保留所选背景资料，默认只携带最近2轮成功对话，简短结论优先；关闭时恢复完整预算历史。没有悄悄删掉背景或改换供应商/模型。
4. 快速模式仅对DeepSeek官方地址应用关闭思考，并去除冲突的reasoning_effort。兼容供应商不自动添加特有参数。官方依据：https://api-docs.deepseek.com/guides/thinking_mode/ 。
5. 明确报告等待接口、等待正文、思考、重试等状态；显示转写收尾、首字、总计。只显示思考阶段，不展示或记录思考正文。
6. 已接受的超时请求不自动重复发送；明确限流/服务错误及连接失败才按配置重试，首个正文后不重试。

降低max_tokens主要影响总输出时间，不保证首字更早。本版不靠强行压低用户的输出上限来掩盖问题。

## 如何定位下一次十秒等待

- 转写收尾很长：本地识别仍在消费音频，检查CPU负载与识别模型大小。
- 等待接口响应很长：网络连接、服务入口或服务端等待；客户端不能保证消除。
- 接口已连接但等待正文很长：服务端排队、推理或上下文处理；确认快速模式、当前模型及历史长度。
- 首字正常但总时间长：答案长度或输出速度，可使用快速简短回答。
- 首字已收到但界面卡：本版已减少逐片段重绘，可提供阶段计时进一步排查。

不通过未经授权的代理或其他账号绕开服务限制，不假装服务端延迟已被完全修复。
